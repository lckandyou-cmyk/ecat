# ECAT 固件升级库使用与 MCU 移植全景工程指南

本指南为嵌入式软件架构师与固件开发工程师提供在 32 位 MCU（如 ARM Cortex-M3/M4/M7、RISC-V 等）上使用 **ECAT (Universal EtherCAT FoE Upgrade Library)** 搭建高可靠独立 Bootloader、完成固件升级协议栈对接与实机部署的完整技术规范。

---

## 1. 核心架构与设计规范

在动手编码前，必须理解本升级库的三大底层设计基石：

1. **零动态内存分配 (Zero Malloc)**：升级状态机与容器解析全流程纯 C99 实现，严禁调用任何动态内存分配函数，内存足迹在编译期确定，杜绝内存碎片与指针泄漏；
2. **物理基地址本地硬编码裁决**：Flash 存储写入基地址与分区容量上限**完全由从站设备本地静态配置决定**。设计上不采信外部 FoE 报文或固件头携带的任何物理地址，从机制上杜绝恶意或损坏的固件越界踩踏 Bootloader 自身代码区；
3. **失效标记先行 (Invalidate First)**：固件头校验通过后、擦除扇区之前，必须先将固件有效标记置为无效；只有全部数据接收完毕、流 CRC 与物理介质回读 CRC 比对一致后，最后才提交有效标记，防止中途断电引导半成品固件。

---

## 2. EtherCAT 状态机 (ESM) 权责与状态划分准则

带独立 Bootloader 的从站设备必须在 **Bootloader** 与 **APP (应用固件)** 之间建立严密的 ESM 状态机权责边界，禁止职能重叠：

```text
               +-------------------------------------------------------+
               |                  INIT (初始化状态)                    |
               |             [Bootloader 与 APP 共同归属]              |
               +-------------------------------------------------------+
                       |                                       ^
        主站发起升级   |                                       | 升级成功切回
        (跳进 Boot)    v                                       | 或复位新固件
               +-----------------------+                       |
               |    BOOT (引导状态)    |                       |
               |  [独家归属于 Bootloader]| ---------------------+
               | (FoE 升级仅在此态运行)|
               +-----------------------+

                       |
         正常运行启动  | (Bootloader 校验通过后跳转进入 APP)
                       v
               +-------------------------------------------------------+
               |           PRE-OP -> SAFE-OP -> OP (运行状态)           |
               |                   [独家归属于 APP]                    |
               |     (过程数据 PDO、应用 CoE 与电机控制仅由 APP 维护)  |
               +-------------------------------------------------------+
```

### 2.1 状态权责归属规范
1. **INIT 态（初始化态）—— 共享归属**：
   - 系统冷启动或硬件复位后的初始状态；
   - 当从站处于 APP 运行态收到主站下发的 `INIT -> BOOT` 请求时，APP 将升级握手魔数存入 Retention RAM / 备份域，并触发系统复位进入 Bootloader；
   - 固件升级顺利完成后，主站下发 `BOOT -> INIT` 状态切换，Bootloader 捕获后触发系统复位并启动新 APP；
2. **BOOT 态（Bootstrap 引导态）—— 独家归属 Bootloader**：
   - **FoE 固件升级只允许且必须在 BOOT 态下执行**；
   - APP 严禁实现或响应 BOOT 态；若在 APP 中收到切入 BOOT 请求，必须由 Bootloader 启动后由 Bootloader 协议栈接管并向 ESC 确认 BOOT 态；
   - Bootloader 只支持 FoE 邮箱通信，不挂载复杂的应用层字典对象与过程数据；
3. **PRE-OP / SAFE-OP / OP 态 —— 独家归属 APP**：
   - 过程数据（PDO）通信、SyncManager 同步、应用层 CoE 字典以及电机控制逻辑**独家由 APP 实现**；
   - Bootloader 严禁尝试切入 Pre-OP 或 OP 状态，升级完毕后只能在 INIT 态交接控制权。

## 3. Bootloader 引导判定与跳转 APP 规范

为了防止固件损坏导致单片机变砖或跳转后发生 HardFault 跑飞，Bootloader 在上电启动时必须执行严格的三路分支裁决，并在执行跳转前完成深度外设与中断清理。

### 3.1 启动三路分支裁决流程
上电复位后，Bootloader 按以下顺序裁决执行分支：
- **分支 A（升级请求进入）**：检查 Retention RAM 或 RTC 备份寄存器中的魔数标记。若存在有效的“升级请求”标记，立即清除该标记，**无条件留在 Bootloader** 启动从站协议栈等待主站下发固件；
- **分支 B（正常固件引导）**：若无升级标记，则对 APP 分区执行**跳转前五重合法性检查**（见 3.2 节）。全部检查通过后，跳转进入 APP 运行；
- **分支 C（固件损坏自愈留守）**：若检查发现固件有效标记失效、堆栈指针越界或入口向量非法（例如新板空片或上次升级中途断电），**严禁跳转，强制留在 Bootloader**，启动协议栈等待主站修复。

### 3.2 跳转前五重检查与深度清理
在执行函数指针跳转前，必须在关闭全局中断的条件下按序执行：

1. **固件有效标记检查 (Valid Magic)**：
   - 读取 Flash 指定元数据区的标志字（如 `APP_FLASH_VALID_MAGIC`）；
   - 确认固件在升级末尾已被完整提交；若标记为无效（`APP_FLASH_INVALID_MAGIC`），拒绝跳转；
2. **主堆栈指针 (MSP) 合法性检查**：
   - 读取 APP 向量表第 0 个字（`*(uint32_t *)APP_FLASH_BASE_ADDR`），即 APP 的初始栈顶地址；
   - 检查该地址是否落在目标 MCU 内部 SRAM 的物理有效区间（如 STM32 的 `0x20000000 ~ 0x20020000`）；若 Flash 处于全 0xFF 状态，该值非法，坚决不跳转；
3. **复位入口向量 (Reset_Handler) 合法性检查**：
   - 读取 APP 向量表第 1 个字（`*(uint32_t *)(APP_FLASH_BASE_ADDR + 4)`），即 APP 的执行入口地址；
   - 检查该地址是否落在 APP 分区的有效 Flash 地址区间内，且最低位必须为 1（ARM Thumb 模式标识）；
4. **升级请求标志清除**：
   - 清除 Retention RAM 或 RTC 备份域中保存的进入 Bootloader 的临时标志，防止下次设备重启时无故反复进入 Bootloader；
5. **系统外设与中断现场清理 (De-init)**：
   - 调用 `__disable_irq()` 关闭全局中断；
   - 关闭 Bootloader 期间启用的所有硬件外设（SPI、PDI 控制器、定时器、DMA、串口调试口等），将相关 GPIO 恢复为默认输入态；
   - **特别注意**：**严禁拉低或触碰外部 ESC 从站控制器的复位引脚 (RST#)**，保证在单片机跳转期间从站网口 PHY 保持持续供电与 Link Up，主站网线不掉线；
   - 清除 NVIC 的所有挂起中断标志 (`NVIC->ICPR`) 与使能位 (`NVIC->ISER`)；
   - 关闭并清零 SysTick 滴答定时器；
   - 重设中断向量表偏移寄存器：`SCB->VTOR = APP_FLASH_BASE_ADDR`；
   - 设置主堆栈指针：`__set_MSP(*(uint32_t *)APP_FLASH_BASE_ADDR)`；
   - 获取入口函数指针并执行跳转：
     ```c
     void (*app_entry)(void) = (void (*)(void))(*(uint32_t *)(APP_FLASH_BASE_ADDR + 4));
     app_entry();
     ```

### 3.3 APP 侧的工程配合要求
1. **链接脚本对齐**：APP 工程的链接脚本（Linker Script，如 `.ld` 或 `.sct`）中，FLASH 的起始地址必须与 Bootloader 定义的 `APP_FLASH_BASE_ADDR` 保持一致，预留出 Bootloader 所占的物理扇区；
2. **向量表重定位**：APP 进入 `main()` 后，第一条执行语句必须再次显式配置 `SCB->VTOR = APP_FLASH_BASE_ADDR`，保证后续中断向量查找正确；
3. **ESC 复位脚隔离**：APP 的板级 GPIO 初始化代码中，同样**严禁拉低外部 ESC 芯片的 RST# 引脚**，避免运行中引起网口掉线。

## 4. 目标存储 Flash 驱动生命周期与契约

用户对接硬件 Flash 驱动需实现 `ecat_foe_target_driver_t` 结构体定义的 8 个函数指针（参考 `examples/bootloader_soes/bootloader_flash_driver.c`），并满足以下生命周期安全契约：

```text
  [WRQ 通过] -> drv->init()
                   | (成功)
                   v
               drv->invalidate()  [清除原有有效标记]
                   |
                   v
    [数据分块] -> drv->erase_to()    [按写入进度向上对齐擦除扇区]
                   |
                   v
               drv->write()       [写入数据至本地基地址偏移处]
                   |
                   v
    [传输结束] -> drv->read()        [从介质物理回读计算 CRC32]
                   |
                   +---> (CRC32 比对一致) -> drv->finalize() [写入有效标志]
                   |
                   +---> (校验失败/中途异常) -> drv->abort()    [保持无效标志]
```

### 4.1 关键契约细则
1. **`init()` 失败自行清理**：若初始化返回非零失败，驱动自行清理资源，核心机设计规则为不调用 `abort()`；
2. **`init()` 成功后异常恰好调用一次 `abort()`**：驱动一旦初始化成功，后续任何阶段失败（擦除、写入、校验或主站中止），核心机调用且仅调用一次 `abort()` 恢复外设安全态；
3. **`invalidate()` 早于擦除执行**：在擦除任何物理扇区前先清除有效标记，防止中途掉电时留下被破坏却带有有效标记的固件；
4. **`erase_to()` 按需推进**：根据写入进度向上按扇区粒度对齐擦除，未执行 `invalidate` 前拒绝擦除，避免一次性全片擦除耗时过长；
5. **本地物理基地址强制偏移**：驱动内部的物理目标地址必须计算为 `APP_FLASH_BASE_ADDR + offset`，杜绝使用报文传来的未经验证的地址。

## 5. 协议栈接入模式深度剖析 (SOES vs SSC)

根据项目采用的 EtherCAT 从站协议栈，选择对应的适配方案：

### 5.1 Simple Open EtherCAT Slave (SOES) 接入规范
- **适配层源码**：`src/adapters/ecat_foe_soes.c` 与 `include/ecat_foe_soes.h`；
- **接入架构**：**前后置邮箱嗅探与中和钩子架构**：
  1. `ecat_foe_soes_pre_process_hook`：在 SOES 协议栈处理前执行，嗅探接收邮箱中的 WRQ，执行只读文件名与元数据预检；
  2. `ESC_foeprocess()`：SOES 原生进程处理，校验密码与 BOOT 态并排队响应；
  3. `ecat_foe_soes_post_process_hook`：检查输出槽位，若核心机激活失败或检测到槽位异常，就地改写为标准 0x8000 错误码并注入复位函数（`FOE_init`）自愈，规避原生 SOES 无 WRQ 回调的缺陷。
- **调度要求**：SOES 协议栈及其前后置钩子非多线程安全，**必须在同一执行流或关中断临界区中串行原子执行**，严禁多任务并发调用。

### 5.2 Beckhoff Slave Stack Code (SSC) 接入规范
- **适配层源码**：`src/adapters/ecat_foe_ssc.c` 与 `include/ecat_foe_ssc.h`；
- **两种运行模式**：
  1. **同步直连模式（强烈推荐）**：单片机片内 Flash 擦写耗时短（几十微秒至数毫秒）时，直接调用 `ecat_foe_ssc_init` 与 `ecat_foe_ssc_on_data`，数据在回调内写入完成并直接返回 0 (ACK)，通信干净流畅；
  2. **异步重试门控模式**：仅用于 Flash 擦除确实耗时较长、必须向主站回复 BUSY 的场合（调用 `ecat_foe_ssc_init_async` 与 `ecat_foe_ssc_on_data_following`）。

## 6. 关键技术暗坑与避坑指南 (Critical Pitfalls)

### 避坑 1：TwinCAT 收到 BUSY 后的“200ms 重试风暴”与 40 秒卡死陷阱

> [!WARNING]
> **真实工况现象**：
> 在实机升级测试中，上位机软件（TwinCAT）每下发一个数据包（如 116 字节），单片机就会持续无脑回复 `BUSY`（Opcode 6）。TwinCAT 收到 BUSY 后，按照 FoE 协议规范会**每隔约 200 毫秒重试发送完全相同的这个数据包**。若单片机一直处于忙碌响应状态，TwinCAT 会持续重试 40 多秒直至上位机单包超时报错！

**为什么单片机会陷入无脑回 BUSY 的死锁？**
1. **主循环漏调轮询驱动**：若开启了异步重试门控（`ecat_foe_ssc_async`），首包进入后状态置为 `pending`。如果单片机的主循环里漏调了 `ecat_foe_ssc_on_main_loop()`，后台任务的状态永远不会被推进完成，导致每次 TwinCAT 重发相同数据包时，单片机只能反复回复 `BUSY`；
2. **底层 Flash 异步状态未正确释放**：如果注册的异步回调 `ops->poll()` 一直返回 `PENDING`（例如硬件寄存器标志未清除或驱动未实际启动），门控会判定任务未完成而持续回复 BUSY；
3. **同步驱动误用了异步门控**：单片机片内 Flash 若是同步阻塞式写入，本应在几十微秒到毫秒级完成，如果误启用了异步重试门控，却没有真正的异步事件通知机制，就会形成空等死锁。

**工程解决建议**：
- **强烈推荐（最稳妥路径）**：若底层 Flash 驱动是同步阻塞操作，**直接使用同步模式初始化**（调用 `ecat_foe_ssc_init`，在数据回调中直接调用 `ecat_foe_ssc_on_data`）。单包数据写入完成后直接返回 0 (ACK)，**坚决避免无脑回复 BUSY**，避开 200ms 重试风暴；
- **异步路径必须满足的条件**：若 Flash 擦除确实耗时较长需要异步返回 BUSY，务必在单片机主循环中高频调用 `ecat_foe_ssc_on_main_loop()`，确保 `ops->poll()` 在物理擦写完成后及时返回 `COMPLETE`，并在超时时主动调用 `abort` 报错中止。

---

### 避坑 2：片内 Flash 擦写导致 CPU 总线冻结 (Bus Stall)
- **风险**：许多 Cortex-M MCU（如 STM32F4/GD32F4 等）在对片内 Flash 执行扇区擦除操作期间，Flash 控制器会冻结 CPU 总线。此时 CPU 停止取指，中断响应暂停；
- **对策**：
  1. 避免在单次回调中执行整片擦除，按需调用 `erase_to` 分步擦除小扇区；
  2. 确保持续通信的协议栈代码和中断向量表位于 SRAM 中执行；
  3. 调整主站 FoE 超时时间以覆盖单扇区擦除的最大硬件耗时。

---

### 避坑 3：原生 SOES 零长度包结束分支忽略写入失败
- **风险**：原生 SOES 在接收到 0 长度结束包时，调用文件关闭回调后直接忽略返回值，依然向主站发送成功 ACK；
- **对策**：
  1. 在打包固件时使用 `efw_pack.py --foe-packet-size N` 进行尾部补齐，确保文件以短包（非 0 长度）收尾，触发原生 SOES 严格检查返回值的短包分支；
  2. 主站端不要仅凭最后一包 ACK 断言固件成功，应在复位前读取从站的应用状态或 CoE 升级结果对象进行二次确认。

---

### 避坑 4：SOES 原生前缀匹配特性
- **风险**：原生 SOES 在匹配 WRQ 文件名时使用 `strncmp`，比对长度取自主站请求中的文件名长度。如果请求短前缀，会错误命中具有相同前缀的文件表项；空文件名无条件命中首条；
- **对策**：从站配置表中的各个文件名表项（如 MCU、FPGA）必须保证前缀互不包含；若无需读取功能，必须显式保持 `FOE_READ_SUPPORTED` 处于未定义状态（切勿定义为 0）。

---

### 避坑 5：完整性校验与安全边界说明
- **风险**：误将 CRC32 视为安全防篡改凭据；
- **事实**：本库采用的 IEEE 802.3 CRC32 仅用于检测通信信道误码与 Flash 介质物理坏块，**不具备防伪造或防恶意篡改能力**；固件头中的 `project_id` 与 `hardware_id` 仅为软硬件兼容性标识，非密码学证书。若应用环境存在防恶意固件注入需求，用户须在固件载荷外增加独立的非对称数字签名验签机制。

## 7. 常见问题诊断与排错速查表

| 故障现象 | 根本原因分析 | 工程处置措施 |
| :--- | :--- | :--- |
| **TwinCAT 发送首个数据包后持续重试 200ms 并卡 40 秒** | 开启了异步重试门控但主循环未调用轮询驱动，或同步 Flash 驱动误用了异步门控 | 改用同步模式 `ecat_foe_ssc_init`；若确需异步，在主循环高频调用 `ecat_foe_ssc_on_main_loop()` |
| **WRQ 阶段直接返回 0x8001 (Not Found)** | 文件名中的项目名称与本地配置 `BOOTLOADER_PROJECT_NAME` 不匹配 | 检查固件打包时传入的 `--project-id` 与文件名是否与从站头文件一致 |
| **数据接收阶段首包返回 0x800B (Program Error)** | 固件头 `hardware_id` 不符、魔数错误、或 Flash `init`/`invalidate` 失败 | 检查硬件板型 ID 配置以及 Flash 存储驱动初始化与擦写函数返回值 |
| **升级提交后设备重启无法运行新 APP (HardFault)** | 固件起始物理地址未对齐，或 APP 工程未将中断向量表重定位至 Flash 分区 | 检查链接脚本中 APP 起始地址是否与 `APP_FLASH_BASE_ADDR` 一致，并确认在 `main()` 开头设置了 `SCB->VTOR` |
| **升级跳转后 TwinCAT 报从站网口掉线 (Link Down)** | Bootloader 在跳转前误将外部 ESC 控制器复位引脚（RST#）拉低 | 严禁触碰或重新初始化 ESC RST# 引脚，保证从站网口 PHY 持续供电 |
