# ECAT 固件升级库使用与 MCU 移植指南

本指南是移植检查清单，不是针对所有 MCU、ESC 和协议栈都成立的完整技术规范。项目提供纯 C FoE 升级核心；板级存储、Bootloader 启动交接、实时安全策略和协议栈接线仍由移植者按具体芯片及协议栈实现并验证。仓库中的宿主测试不等于真实硬件或主站验证。

---

## 1. 核心架构与设计规范

移植时应先确认以下核心行为及其适用边界：

1. **无动态内存的核心实现**：FoE 升级状态机与容器解析核心使用纯 C99 且不调用动态内存分配。移植层和协议栈仍需自行管理各自的资源；实际 RAM/Flash 占用需在目标工具链上测量；
2. **写入范围由本地分区配置决定**：升级核心不使用 FoE 请求或固件头提供的物理写地址。目标驱动仍必须校验本地分区范围、偏移加法溢出及介质约束；正确配置和边界检查是防止越界写入的必要条件，不等于固件真实性验证；
3. **先失效、校验后提交**：在擦除目标镜像前将其有效状态置为无效；仅在接收完成且流 CRC 与介质回读 CRC 一致后提交有效状态，以降低断电后误启动不完整镜像的风险。实际掉电安全性取决于目标驱动和元数据写入设计。

---

## 2. EtherCAT 状态机 (ESM) 权责与状态划分准则

带独立 Bootloader 的设备应明确 Bootloader 与 APP 各自负责的 EtherCAT 状态、邮箱服务和复位/交接方式。具体状态迁移取决于 ESC、协议栈配置及设备架构；以下只是需要移植者核实的设计选项，不是 EtherCAT 或本库强制的统一状态模型：

```text
               +-------------------------------------------------------+
               |                  INIT (初始化状态)                    |
               |            [按产品定义交接与归属]                     |
               +-------------------------------------------------------+
                       |                                       ^
        主站发起升级   |                                       | 升级成功切回
        (跳进 Boot)    v                                       | 或复位新固件
               +-----------------------+                       |
               |    BOOT (引导状态)    |                       |
               | [示意：Bootloader 提供 FoE] | --------------------+
               | (FoE 升级仅在此态运行)|
               +-----------------------+

                       |
         正常运行启动  | (Bootloader 校验通过后跳转进入 APP)
                       v
               +-------------------------------------------------------+
               |           PRE-OP -> SAFE-OP -> OP (运行状态)           |
               |              [示意：APP 运行态]                       |
               |     (过程数据 PDO、应用 CoE 与电机控制仅由 APP 维护)  |
               +-------------------------------------------------------+
```

### 2.1 状态权责归属规范
1. **INIT 态（初始化态）—— 按产品设计交接**：
   - 系统冷启动或硬件复位后的初始状态；
   - 若产品通过复位进入 Bootloader，可使用目标 MCU 确认过的备份域/Retention RAM 标志或其他平台机制传递请求；标志应带版本/完整性校验，并在安全的时机清除；
   - 升级后的复位或 ESM 迁移顺序必须结合协议栈与 ESC 的实际行为定义并验证，不假定 Bootloader 总能直接捕获 `BOOT -> INIT`；
2. **BOOT 态（Bootstrap 引导态）—— 按产品架构分配**：
   - 若设备把 FoE 下载限制在 BOOT/Bootstrap 态，Bootloader 必须按所用协议栈和 ESC 的状态机契约提供相应邮箱服务；其他状态下是否启用 FoE 由产品和协议栈配置决定；
   - 若产品将 BOOT 态交给独立 Bootloader，通常只启用升级所需的邮箱服务；是否挂载其他对象由产品架构决定；
3. **PRE-OP / SAFE-OP / OP 态 —— 按产品定义**：
   - 过程数据（PDO）通信、SyncManager 同步、应用层 CoE 字典以及电机控制逻辑通常由 APP 实现；若产品有不同划分，必须在协议栈接入设计中明确；
   - Bootloader 是否支持其他 ESM 状态由产品架构决定；不能把本示意图当作协议栈自动交接的保证。

### 2.2 FOC / 电机控制从站安全下电联动规范
在伺服驱动器与 FOC 等设备中，升级入口和复位前动作必须遵循产品安全分析及驱动器硬件设计。是否禁能 PWM、如何处理 STO/制动器、是否保存运行状态及状态迁移顺序都属于设备级决策；本库不能替设备规定这些安全动作。不得未经安全审查就把运行参数写入非易失存储或改变执行器状态。

## 3. Bootloader 引导判定与跳转 APP 规范

为了防止固件损坏导致单片机变砖或跳转后发生 HardFault 跑飞，Bootloader 在上电启动时必须执行严密的三路分支裁决，并在执行跳转前完成深度外设与中断清理。

### 3.1 启动三路分支裁决流程
上电复位后，Bootloader 按以下顺序裁决执行分支：
- **分支 A（升级请求进入）**：检查 Retention RAM 或 RTC 备份寄存器中的有效“升级请求”标记。若存在，**留在 Bootloader** 启动从站协议栈等待主站下发固件；仅在 Bootloader 已可靠接管升级服务后，才按产品定义清除该请求标记；
- **分支 B（正常固件引导）**：若无升级请求，则对 APP 分区执行 3.2 节所列检查。全部检查通过后，跳转进入 APP 运行；
- **分支 C（固件损坏自愈留守）**：若检查发现固件有效标记失效、堆栈指针越界或入口向量非法（例如新板空片或上次升级中途断电），**严禁跳转，强制留在 Bootloader**，启动协议栈等待主站修复。

### 3.2 Cortex-M 跳转前检查与现场清理
以下仅为 Cortex-M 检查项；其他 CPU 架构必须使用其自己的启动和跳转规则。向量表地址、可用 SRAM 区间、栈对齐、外设清理以及中断状态都必须依据具体 MCU 参考手册和启动代码确认：

1. **固件有效标记检查 (Valid Magic)**：
   - 读取 Flash 指定元数据区的标志字（如 `APP_FLASH_VALID_MAGIC`）；
   - 确认固件在升级末尾已被完整提交；若标记为无效（`APP_FLASH_INVALID_MAGIC`），拒绝跳转；
2. **主堆栈指针 (MSP) 合法性检查**：
   - 读取 APP 向量表第 0 个字（`*(uint32_t *)APP_FLASH_BASE_ADDR`），即 APP 的初始栈顶地址；
   - 检查该地址是否落在该具体器件允许作为 MSP 的 SRAM 区间，并满足栈对齐要求。不同 SRAM 区块可能有不同总线/用途限制；不能用一个 STM32 地址范围代表整个系列；
3. **复位入口向量 (Reset_Handler) 合法性检查**：
   - 读取 APP 向量表第 1 个字（`*(uint32_t *)(APP_FLASH_BASE_ADDR + 4)`），即 APP 的执行入口地址；
   - 检查该地址是否落在 APP 分区的有效 Flash 地址区间内，且最低位必须为 1（ARM Thumb 模式标识）；
4. **系统外设与中断现场清理 (De-init)**：
   - 调用 `__disable_irq()` 关闭全局中断；
   - 关闭 Bootloader 期间启用的所有硬件外设（SPI、PDI 控制器、定时器、DMA、串口调试口等），将相关 GPIO 恢复为默认输入态；
   - ESC 是否需要保持供电、复位或重新初始化取决于电路连接及期望的 EtherCAT 重启行为；必须按板级设计验证，不能通用规定“绝不触碰复位脚”；
   - 按目标 MCU 实现的 IRQ 数量，使用 NVIC `ICER` 禁用外部中断、使用 `ICPR` 清除挂起状态；`ISER` 是置使能寄存器，不能用来清除使能位；
   - 关闭并清零 SysTick 滴答定时器；
   - 在跳转前按具体 MCU 要求配置向量表基址；需要时还应再次校验镜像或签名；升级请求标志的清除时机按 3.1 节和产品启动设计处理；
   - **不得**在普通 C 函数中调用 `__set_MSP(app_msp)` 后再执行 `app_entry()`。切换 MSP 后，编译器生成的函数调用、栈帧和返回路径可能使用新栈或尝试返回 Bootloader；应由目标专用、不可返回的汇编启动桩原子完成 MSP 设置和分支（例如在寄存器中准备 MSP/Reset_Handler 后执行 `MSR MSP, ...` 与 `BX ...`），并按具体内核设置 CONTROL、栈限制寄存器等状态。

### 3.3 APP 侧的工程配合要求
1. **链接脚本对齐**：APP 工程的链接脚本（Linker Script，如 `.ld` 或 `.sct`）中，FLASH 的起始地址必须与 Bootloader 定义的 `APP_FLASH_BASE_ADDR` 保持一致，预留出 Bootloader 所占的物理扇区；
2. **向量表重定位**：若目标使用可重定位向量表，应在启动代码启用中断前设置向量表地址；在 `main()` 设置可能太晚；
3. **ESC 复位策略**：APP 对 ESC 复位脚的处理应与板级电路、ESC 初始化和预期链路恢复行为一致。

### 3.4 硬件看门狗 (IWDG) 跨阶段生命周期协同
1. **硬件差异**：许多 MCU 的独立看门狗在启动后不能停止或只能通过特定复位停止；按目标芯片参考手册确认，不能泛化到所有 Cortex-M 器件；
2. **Bootloader 擦写期喂狗**：Flash 大扇区擦除时间可达数百毫秒甚至数秒。驱动中若有大范围擦写，必须在分段擦除循环中显式插入喂狗调用，避免因总线冻结或通信等待导致看门狗超时复位；
3. **APP 启动初期接管**：Bootloader 跳转后，APP 的启动代码会先执行 C 运行时初始化，再到达 `main()`；若看门狗超时可能短于这段时间，应在目标启动汇编中安排可行的喂狗策略，或调整 Bootloader/APP 交接设计。不要假设 `main()` 第一行能覆盖 C 运行时之前的延迟，也不要假设 IWDG 可重新配置。

### 3.5 SRAM 内存边界规划与脏数据隔离
1. **RAM 空间划分**：
   - Bootloader 与 APP 是否共享 SRAM、哪些区块跨复位保留，都由 MCU 和启动配置决定。若用 `.noinit` 或备份域传递引导参数，应确认复位/掉电保持语义，并加入版本、完整性校验和失效处理；不能假设普通 SRAM 在掉电后保留；
2. **堆栈指针重设**：由目标专用、不可返回的汇编跳转桩将 MSP 设置为 APP 向量表首字的值并直接分支到 Reset_Handler；不要在切换 MSP 后继续执行普通 C 调用链；
3. **防止残留脏变量**：APP 链接脚本必须将自身的 `.bss` 段清零，避免 Bootloader 运行期间留在 RAM 中的变量数据干扰 APP 运行。

## 4. 目标存储 Flash 驱动生命周期与契约

用户对接同步目标存储驱动需按 `ecat_foe_target_driver_t` 中的 7 个回调实现所需操作（参考 `examples/bootloader_soes/bootloader_flash_driver.c`），并遵守以下生命周期契约：

```text
  [WRQ 通过] -> drv->init()
                   | (成功)
                   v
               drv->invalidate()  [清除原有有效标记]
                   |
                   v
    [数据分块] -> drv->erase_to()    [按写入进度向上对齐擦除扇区]
                   |
                   v
               drv->write()       [写入数据至本地基地址偏移处]
                   |
                   v
    [传输结束] -> core 调用 drv->read()，由核心计算回读 CRC32
                   |
                   +---> (CRC32 比对一致) -> drv->finalize() [写入有效标志]
                   |
                   +---> (校验失败/中途异常) -> drv->abort()    [保持无效标志]
```

### 4.1 关键契约细则
1. **`init()` 失败自行清理**：若初始化返回非零失败，驱动自行清理资源，核心机设计规则为不调用 `abort()`；
2. **`init()` 成功后异常恰好调用一次 `abort()`**：驱动一旦初始化成功，后续任何阶段失败（擦除、写入、校验或主站中止），核心机调用且仅调用一次 `abort()` 恢复外设安全态；
3. **`invalidate()` 早于擦除执行**：在擦除任何物理扇区前先清除有效标记，防止中途掉电时留下被破坏却带有有效标记的固件；
4. **`erase_to()` 按需推进**：根据写入进度向上按扇区粒度对齐擦除，未执行 `invalidate` 前拒绝擦除，避免一次性全片擦除耗时过长；
5. **本地分区配置强制裁决**：具体驱动应使用本地配置的分区基址加相对 `offset`，并检查加法溢出及分区边界；`APP_FLASH_BASE_ADDR` 仅是 MCU 示例中的名称，不适用于所有目标（例如 FPGA 外存或 EEPROM）。不得采用 FoE 报文提供的物理写地址。

### 4.2 Flash 物理写入对齐与 ECC 陷阱规避
1. **写入粒度**：编程宽度、地址对齐、ECC word 大小和重复编程限制因具体料号、供电/编程模式及 Flash bank 而异。驱动必须依据目标器件的数据手册、参考手册和厂商库定义实现对齐；不要把 STM32F4/G4/H7 整个系列概括为固定字节宽度。例如 STM32H7 不同子系列的 Flash word/ECC 粒度并不相同；
2. **重复编程限制**：部分带 ECC 的 Flash 不允许同一编程单元在一次擦除周期内重复编程，可能导致编程失败、ECC 错误或数据不可靠。按具体器件手册和厂商 API 实现；驱动应跟踪擦除与写入粒度，避免未经支持的重复编程。

## 5. 协议栈接入模式深度剖析 (SOES vs SSC)

根据项目采用的 EtherCAT 从站协议栈，选择对应的适配方案：

### 5.1 Simple Open EtherCAT Slave (SOES) 接入规范
- **适配层源码**：`src/adapters/ecat_foe_soes.c` 与 `include/ecat_foe_soes.h`；
- **接入架构**：**前后置邮箱嗅探与中和钩子架构**：
  1. `ecat_foe_soes_pre_process_hook`：在 SOES 协议栈处理前嗅探接收邮箱中的 WRQ，并对核心状态与驱动无副作用地预检文件名和元数据；钩子会暂存 WRQ，并临时调整 SOES 文件表条目/计数以路由请求，随后由后置流程恢复文件计数；
  2. `ESC_foeprocess()`：SOES 原生进程处理，校验密码与 BOOT 态并排队响应；
  3. `ecat_foe_soes_post_process_hook`：检查输出槽位，若核心机激活失败或检测到槽位异常，就地改写为标准 0x8000 错误码并注入复位函数（`FOE_init`）自愈，规避原生 SOES 无 WRQ 回调的缺陷。
- **调度要求**：SOES 协议栈及其前后置钩子非多线程安全，**必须在同一执行流或关中断临界区中串行原子执行**，严禁多任务并发调用。

### 5.2 Beckhoff Slave Stack Code (SSC) 接入规范
- **适配层源码**：`src/adapters/ecat_foe_ssc.c` 与 `include/ecat_foe_ssc.h`；
- **两种运行模式**：
  1. **同步模式**：当前已接入核心的路径由 `ecat_foe_ssc_init` 与 `ecat_foe_ssc_on_data` 调用同步核心和目标驱动。是否能满足响应时限，应测量目标驱动最坏耗时及主站/协议栈限制；不能仅按“片内 Flash”假定耗时足够短；
  2. **异步门控原语（尚非端到端异步升级）**：`ecat_foe_ssc_init_async` 与 `ecat_foe_ssc_on_data_following` 提供单包 BUSY/重试门控，但仓库当前未将其与 `ecat_foe_core` 和完整异步存储状态机接通。单独使用这些接口不能完成库的异步 FoE 升级。完整核心接入前，移植者若自行实现异步处理，必须自行承担状态机、数据校验及最终 ACK 的正确性。

### 5.3 ESC 芯片与 Mailbox SyncManager 配置生命周期管理
1. **按状态核实 Mailbox/SyncManager 配置**：
   - BOOT 与 PRE-OP / SAFE-OP / OP 状态下的邮箱大小、地址和 SyncManager 分配由 ESC、协议栈及设备描述配置决定，不能假定 BOOT 邮箱固定为 1024 字节或状态切换时必然缩减；
   - 分别核对 Bootloader 与 APP 使用的 ESC 内存布局，并确认 FoE 请求/响应容量与过程数据区域不冲突；
2. **EEPROM (SII) 保护**：
   - 本库可将 FoE 目标映射到本地配置的 MCU、FPGA 或 EEPROM 存储。SII/ESC 配置 EEPROM 是否开放为升级目标必须显式设计和启用；不要把修改 SII 配置与 MCU 固件 FoE 下载混为一谈，误写 SII 可能导致从站配置异常。

## 6. 关键技术暗坑与避坑指南 (Critical Pitfalls)

### 避坑 1：异步 BUSY/重试必须按主站实测配置

> [!WARNING]
> `BUSY`/重试间隔与总超时取决于主站实现和配置。不要把特定环境观察到的重试周期或总耗时当作 FoE 协议的通用保证；在目标主站、版本和配置上记录实际响应及超时。

**用户实机观测（特定测试环境）**：用户报告一次真实升级中，从站对数据包返回 `BUSY` 后，主站约 200 ms 再次发送当前包；这一过程反复发生，整次升级耗时接近 40 秒。这里的 200 ms 是该环境观测到的主站重试间隔，近 40 秒是整次升级耗时，不代表单包超时或所有主站的固定行为。

**与当前仓库代码的关系**：SSC 异步门控在匹配包仍处于 pending 时立即返回初始化时配置的 `busy_foe_code`；它不负责等待 200 ms，重发时序由主站控制。`timeout_ticks` 是单个 pending 操作的超时，不是整次升级的总时限。当前仓库没有把这个门控接入完整 FoE 核心升级流程，异步初始化/调用只出现在 Mock 测试中；现有 Bootloader 示例走同步 SOES 路径。因此上述实机现象是用户测试记录，不能仅凭当前仓库证明具体是哪一个回调或超时配置造成。要复现归因，还需记录实际回调接线、BUSY 码、`timeout_ticks`、poll 结果、主站版本和抓包时间戳。

**为什么单片机会陷入无脑回 BUSY 的死锁？**
1. 若已实现并接入异步核心，漏调主循环 poll 会让 pending 操作无法推进；
2. 驱动若持续报告 pending，适配层会继续返回配置的 BUSY，直到完成或超时；
3. 当前仓库的 SSC 门控和异步目标操作层尚未接入异步 `ecat_foe_core` 升级状态机。仅初始化门控不等于异步 Flash 升级。

**工程解决建议**：
- 对同步驱动使用同步核心路径，并测量回调最长耗时是否符合主站和协议栈时限；不要仅凭“片内 Flash”推断时长。
- 在异步核心完成并集成前，不要将当前 SSC 门控描述为可直接进行异步固件升级。完整异步实现还须验证 BUSY 返回码、重试包身份、poll 调度、超时清理和最终 ACK 时序。

### 避坑 2：目标 MCU 的 Flash 擦写执行影响
- **风险**：Flash 擦写期间 CPU、取指、总线仲裁和中断可用性由具体 MCU、bank/dual-bank 配置、执行区域及缓存配置决定；不能仅凭 MCU 系列名称判断一定发生总线冻结；
- **对策**：
  1. 避免在单次回调中执行整片擦除，按需调用 `erase_to` 分步擦除小扇区；
  2. 查阅目标芯片手册并测量擦写期间的通信/中断行为；只有芯片支持且工程验证需要时，才将相关代码、数据或中断向量放入可执行 SRAM 区；
  3. 在主站支持的范围内配置超时，并以实测最大擦除/写入耗时留出余量。

---

### 避坑 3：SOES 结束包分支需按实际版本核对
- **风险**：仓库所核对的 SOES 源码版本中，某些零长度结束路径对回调错误的处理与短包路径不同；不同版本/分支需重新核对，不能泛称所有“原生 SOES”；
- **对策**：
  1. 若所用协议栈版本确有该差异，可使用 `efw_pack.py --foe-packet-size N` 生成与邮箱载荷匹配的填充文件，并验证最终 DATA 分包确实走预期分支；
  2. 主站端不要仅凭最后一包 ACK 断言固件成功，应在复位前读取从站的应用状态或 CoE 升级结果对象进行二次确认。

---

### 避坑 4：SOES 文件名匹配需核对目标版本
- **风险**：仓库引用的 SOES 版本在特定配置下使用请求长度执行 `strncmp`，可产生短前缀/空名称匹配风险；这不是对所有 SOES 分支的保证；
- **对策**：检查实际使用版本的文件查找实现和配置。若代码使用 `#ifdef FOE_READ_SUPPORTED`，关闭读取应保持宏未定义，而不是定义为 0；文件名唯一性不能替代精确匹配检查。

---

### 避坑 5：完整性校验与安全边界说明
- **风险**：误将 CRC32 视为安全防篡改凭据；
- **事实**：本库采用的 IEEE 802.3 CRC32 用于检测意外数据损坏及回读不一致；CRC 不识别损坏原因，也**不具备防伪造或防恶意篡改能力**。固件头中的 `project_id` 与 `hardware_id` 仅为软硬件兼容性标识，非密码学证书。若应用环境存在防恶意固件注入需求，用户须在固件载荷外增加经过设计的固件签名验证机制。

---

### 避坑 6：EEPROM (SII) 烧录与 FoE 固件升级混淆
- **风险**：在上位机操作时，误将从站 MCU 固件文件下载到 ESC 的 EEPROM 中，造成硬件 SII 数据错乱；
- **对策**：严格区分 TwinCAT 菜单中的 "Write EEPROM" 与 "Download via FoE"。FoE 固件下载必须进入从站的 Online 属性页的 "Bootstrap" -> "Download" 窗口进行操作。

## 7. 上位机 (TwinCAT) 实机操作手册与联调配置

以下为需在目标 TwinCAT/从站组合上确认的操作流程示意；菜单名称、Boot 状态入口和设备响应会随 TwinCAT 版本及设备描述变化：

1. **扫描并识别从站**：在 TwinCAT I/O 树中扫描并发现目标从站设备；
2. **切入 Bootstrap (BOOT) 态**：
   - 选中该从站，切换到 **Online** 选项卡；
   - 在 State Machine 区域点击 **Init**，随后点击 **Bootstrap**；
   - 观察 Current State 是否变为 `BOOT`；该状态显示本身不能单独证明 MCU Bootloader 已成功接管，需结合设备日志/状态确认；
3. **打开 FoE 下载对话框**：
   - 在 Online 界面点击 **Download...** 按钮；
   - 选择 `efw_pack.py pack` 生成的有效容器文件（通常为 `*.efw`）；原始 `*.bin` 是打包输入，不能直接当作包含 EFW 头的 FoE 容器上传，除非设备另有明确支持；
   - 在 Edit FoE Name 对话框中输入请求文件名，必须符合本地解析规则中的工程名、目标名、版本和小写 `.efw` 扩展名，例如 `SERVO_DRV_MCU_V1.0.0.0.efw`；工程名对应打包参数 `--project-name`（通常与 `BOOTLOADER_PROJECT_NAME` 相同），不是数值型 `--project-id`；
   - 若从站启用了密码保护，填入对应的十六进制密码（Password）；
4. **监控下载进度**：
   - 点击 OK 开始传输。观察 TwinCAT 状态栏传输进度条；
   - 传输完成后，TwinCAT 会提示下载成功；
5. **切回 INIT 触发系统启动**：
   - 在 State Machine 区域点击 **Init**；
   - 按设备定义执行状态切换或复位；不要假设所有从站都通过捕获 `BOOT -> INIT` 自动启动新 APP。

## 8. 固件容灾与高可靠升级模型对比

根据从站硬件资源与可靠性等级要求，可选用两种典型固件部署方案：

| 方案维度 | 单分区留守方案 (In-Place Overwrite) | 双分区回退方案 (A/B Ping-Pong) |
| :--- | :--- | :--- |
| **Flash 资源占用** | 仅需 1 份 APP 容量（适合小 Flash MCU） | 需至少 2 份 APP 容量（适合大容量 MCU） |
| **升级中断影响** | 若目标镜像有效标记能可靠失效，设备可留在 Bootloader 等待重新烧录 | 若仅写入非活动分区且切换逻辑正确，原分区可保留 |
| **回滚能力** | 不提供 APP 镜像回滚；需由 Bootloader 恢复或重新下载 | 只有实现活动分区选择、启动健康判定与回退元数据后，才能自动回滚 |
| **推荐适用场景** | 成本敏感型通用伺服、普通 IO 从站 | 高可用连续生产线、严苛工业现场驱动器 |

## 9. 常见问题诊断与排错速查表

| 故障现象 | 根本原因分析 | 工程处置措施 |
| :--- | :--- | :--- |
| **TwinCAT 发送 DATA 后持续重试或超时** | 可能是主站与从站 BUSY/ACK 时序不匹配、异步 poll 未推进、操作耗时过长或 FoE 文件包不匹配 | 记录主站版本、实际 FoE 响应与时间戳；当前异步门控尚未接入完整核心，先用已接入的同步路径，或由移植者自行实现并验证完整异步核心 |
| **WRQ 阶段直接返回 0x8001 (Not Found)** | 请求文件名中的工程名/目标/版本/扩展名与本地规则不匹配，或目标未启用 | 核对请求文件名是否与打包器输出文件名一致；用 `--project-name` 设置文件名前缀，`--project-id` 是独立的数值型固件元数据，不控制 WRQ 文件名匹配 |
| **数据接收阶段首包返回 0x800B (Program Error)** | 固件头 `hardware_id` 不符、魔数错误、或 Flash `init`/`invalidate` 失败 | 检查硬件板型 ID 配置以及 Flash 存储驱动初始化与擦写函数返回值 |
| **升级提交后设备重启无法运行新 APP (HardFault)** | 可能涉及镜像/分区错误、MSP/Reset_Handler 无效、启动桩或向量表配置不匹配 | 检查本地分区映射、向量内容和目标启动流程；若需重定位 VTOR，应在启动代码启用中断前设置 |
| **升级跳转后 TwinCAT 报从站网口掉线 (Link Down)** | 可能涉及 MCU/ESC 复位、电源、PDI 初始化或链路恢复策略 | 根据原理图和 ESC 接口检查复位/电源/PDI 时序及协议栈重启行为，不预设唯一原因 |
| **Flash 擦写时偶发 HardFault 或数据校验错误** | 可能涉及对齐、bank/ECC 粒度、重复编程、缓存或芯片错误状态 | 对照具体料号手册和厂商 API 检查写入粒度、擦除状态、错误标志及缓存处理 |
| **Bootloader 升级中途设备异常复位重启** | 硬件看门狗 (IWDG) 超时复位 | 在分段擦除与数据处理循环中加入定期喂狗指令 |
