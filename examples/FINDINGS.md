# 示例开发架构发现与 API 完备性评估 (Architecture Findings)

本文档记录在开发宿主参考示例（`examples/host_demo`）与驱动模板（`examples/driver_template`）过程中的技术发现、API 评估及局限性说明。

## 1. 核心公开 API 完备性与驱动契约评估

在不修改核心公开 API（`include/ecat_foe_core.h`）的前提下，实现宿主机参考示例（涵盖 8 类核心场景）的评估结论如下：

- **现有 API 完备可用**：
  - `ecat_foe_core_init`：负责校验全局配置（项目 ID、硬件 ID、版本下限防回滚设置、目标驱动表）并初始化内部状态；支持用户注册多目标（如 Target 1 板载 Flash，Target 2 外部 SPI Flash 可选目标）；
  - `ecat_foe_core_on_wrq`：完成文件名解析、项目名称匹配、目标定位及防回滚版本检查；
  - `ecat_foe_core_on_data`：完成固定 148 字节 v2 头部装配校验（魔数、CRC、全量元数据）、驱动初始化（`init`、`invalidate`）、按需擦除和分块写入；结束时进行回读校验；启用验签时，提交前还会对存储回读载荷验签；
  - `ecat_foe_core_on_end`：完成长度和回读校验；启用时验签，再调用普通提交或防回滚联合提交；
  - `ecat_foe_core_on_abort`：完成故障中止时的驱动清理回调调用，并将核心状态恢复为 `ECAT_FOE_STATE_IDLE`，支持在同一个 core 实例上接收新会话重试。
- **驱动契约与防变砖安全机制**：
  - `init()` 为非破坏性操作：仅打开外设句柄，严禁以截断模式破坏现有数据；
  - 在擦除与写入之前，旧固件数据与有效标记保持完好且可观察；
  - 核心在头部校验全过后才调用 `invalidate()`，将有效标记置为无效；
  - 驱动的 `erase_to()` 在未置无效前拒绝执行擦除；
  - 流 CRC 与回读 CRC32 通过、启用时验签也通过后，普通模式由 `finalize()` 提交；防回滚模式使用板级联合事务；
  - 针对文件 I/O 关闭操作引入 `safe_file_close()`，先执行 `fflush()` 后执行 `fclose()`，杜绝因逻辑或短路求值导致的文件句柄泄漏；
  - 示例程序对当前工作目录零副作用，所有介质文件严格限定在系统临时隔离目录内，外部测试严密验证预存同名哨兵文件的完整性与多实例并发隔离；
  - Makefile 构建安全性升级：`test-examples` 目标的所有中间构建产物（二进制、对象文件、打包固件与运行输出）均被约束在系统独立临时构建目录中，利用 shell trap 确保无论成功失败均只清理自身目录，绝不污染或覆盖源码树；在预存 7 大同名哨兵文件的隔离仓库副本中，验证了 `make test-examples`、`make test` 与并发构建执行后所有哨兵字节完整不变。

## 2. 真实协议栈交互观察与局限说明

### 2.1 原生 SOES 零长度结束包路径返回值忽略
- **宿主观察现象**：
  在原生 SOES（`esc_foe.c`）中，当传输数据总长恰好是邮箱载荷整数倍时，传输以零长度数据包结束。在此路径下，SOES 调用 `FOE_fclose` 后未检查其返回值，直接回复 FoE ACK。
- **保护效果**：
  在核心机层面，若底层 `finalize` 失败，`ecat_foe_core_on_end` 正确返回 -1 并转入 `ECAT_FOE_STATE_ERROR`，底层介质上无有效标记。因此 Bootloader 启动检测时不会引导损坏固件。但在通信层，主站不会收到 0x800B 报错。该协议栈现象已在 `tests/test_soes_real_harness.c` 中通过真实 `esc_foe.c` 独立验证。
- **规避方案**：
  工具端使用 `efw_pack.py --foe-packet-size N` 在尾部按目标追加 `0xFF`，尽力规避整数倍结束包；实际分包和主站可观察结果仍需实测。场景 7 在宿主验证打包文件与核心接收。

### 2.2 生产环境中 WRQ 阶段的路由现实与架构演进
- **宿主观察现象**：
  在原生 SOES 中，主站发送 WRQ 时，SOES 协议栈立即回复 ACK(0)，并没有向上层应用提供预检回调钩子。
  若直接使用原生文件回调，当首块数据到达时 SOES 才调用注册的文件写入回调。若此时文件名或头部非法，只能在数据阶段返回 0x800B（`FOE_ERR_PROGERROR`），而无法在 WRQ 阶段回复 0x8001（`FOE_ERR_NOTFOUND`）。
- **示例与测试中的处理及演进**：
  - 宿主示例通过子场景 3a 与 3b，分别展示了 WRQ 阶段项目名不符（核心拒绝并置 `WRQ_PROJECT_MISMATCH`）与 WRQ 通过但头部 `project_id` 不符（核心在阶段 3 全量核验拒绝并置 `HDR_VERIFY`）的防御能力；
  - 早期基础适配层曾采用在首包数据到达时触发检查；而在现行方案中，SOES 适配层（`src/adapters/ecat_foe_soes.c`）已引入前后置邮箱钩子架构（`ecat_foe_soes_pre_process_hook` 与 `ecat_foe_soes_post_process_hook`），前置嗅探 WRQ 并做只读预检，若核心激活失败或响应异常，后置钩子就地将排队的 ACK(0) 改写为标准 `FOE_OP_ERR (0x8000)` 并注入复位自愈，实现了零侵入的 WRQ 错误阻断。

## 3. 宿主示例边界说明

- **无掉电安全性保证**：宿主示例使用本地普通文件模拟 Flash 存储，未实现针对断电保护的硬件原子性操作或双区乒乓备份机制；
- **非硬件/MCU 实测**：仅在 x86_64/arm64 宿主操作系统上执行单元验证，未在真实 MCU、真实 ESC 硬件或生产总线环境下进行实机验证；
- **校验边界澄清**：内置 CRC32 流式计算与物理回读仅用于数据传输与介质存储的意外损坏检测，不具备密码学防伪造、防篡改或身份认证能力；可选 Ed25519ph 验签可认证固件来源，默认关闭，须配置可信公钥与后端；设备身份认证和安全启动仍需由产品实现；
- **独立性与无外部依赖保证**：不依赖外部临时源码目录（如 `/tmp/soes_src`），所有宿主示例均可由本仓库独立编译构建与重复验证；
- **契约与协议中立性**：遵循已授权范围，未擅自预设固定文件名协议或改动核心公开 API 签名与接口行为。
