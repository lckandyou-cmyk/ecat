# 示例开发架构发现与 API 完备性评估 (Architecture Findings)

本文档记录在开发宿主参考示例（`examples/host_demo`）与驱动模板（`examples/driver_template`）过程中的技术发现、API 评估及局限性说明。

## 1. 核心公开 API 完备性评估

在不修改核心公开 API（`include/ecat_foe_core.h`）的前提下，实现宿主机参考示例（涵盖 8 类核心场景）的评估结论如下：

- **现有 API 完备可用**：
  - `ecat_foe_core_init`：负责校验全局配置（项目 ID、硬件 ID、版本下限防回滚设置、目标驱动表）并初始化内部状态；
  - `ecat_foe_core_on_wrq`：完成文件名解析、项目名称匹配、目标定位及防回滚版本检查；
  - `ecat_foe_core_on_data`：完成 64 字节头部装配校验（魔数、CRC、全量元数据）、驱动初始化（`init`、`invalidate`、`erase_to`）、分块写入与逐块回读校验；
  - `ecat_foe_core_on_end`：完成实际接收长度校验、驱动落盘收尾（`finalize`）与版本下限持久化；
  - `ecat_foe_core_on_abort`：完成故障中止时的驱动清理回调调用。
- **无需新增或修改任何核心 API**：现有公开 API 支持驱动在外部注入模拟上下文、接收分块数据流、检测各类数据损坏以及在同一 core 实例上发起新 WRQ 重试。

## 2. 真实协议栈交互观察与局限说明

### 2.1 原生 SOES 零长度结束包路径返回值忽略
- **宿主观察现象**：
  在原生 SOES（`esc_foe.c`）中，当传输数据总长恰好是邮箱载荷整数倍时，传输以零长度数据包结束。在此路径下，SOES 调用 `FOE_fclose` 后未检查其返回值，直接回复 FoE ACK。
- **保护效果**：
  在核心机层面，若底层 `finalize` 失败，`ecat_foe_core_on_end` 正确返回 -1 并转入 `ECAT_FOE_STATE_ERROR`，底层介质上无有效标记。因此 Bootloader 启动检测时不会引导损坏固件。但在通信层，主站不会收到 0x800B 报错。
- **规避方案**：
  工具端使用 `efw_pack.py --foe-packet-size N` 进行尾部补零填充，确保末包为短包（非零长度），从而触发带返回值检查的短包结束路径，使失败能够被主站捕获（返回 0x800B）。

### 2.2 生产环境中 WRQ 阶段的路由现实
- **宿主观察现象**：
  在原生 SOES 中，主站发送 WRQ 时，SOES 协议栈立即回复 ACK(0)，并没有向上层应用提供预检回调钩子。
  当首块数据到达时，SOES 才调用注册的文件写入回调。若此时文件名或头部非法，只能在数据阶段返回 0x800B（`FOE_ERR_PROGERROR`），而无法在 WRQ 阶段回复 0x8001（`FOE_ERR_NOTFOUND`）。
- **示例与测试中的处理**：
  宿主示例直接调用核心公开接口 `ecat_foe_core_on_wrq`，展示了核心状态机的标准握手逻辑。在 SOES 适配层（`ecat_foe_soes.c`）中，则是首包到达时自动触发该检查。

## 3. 宿主示例边界说明

- **无掉电安全性保证**：宿主示例使用本地普通文件模拟 Flash 存储，未实现针对断电保护的原子日志或双区乒乓备份机制；
- **非硬件/MCU 实测**：仅在 x86_64/arm64 宿主操作系统上执行单元验证，未在真实 MCU、真实 ESC 硬件或生产总线环境下进行实机验证。
